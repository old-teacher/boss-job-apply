# BOSS 直聘投递助手（boss姥爷）

## 概述

按个人画像在 BOSS 直聘网页端检索并筛选岗位：按关键词顺序轮转检索，每个关键词全量采完再走复核投递闭环；明确对口的发默认招呼语；不确定/边缘岗位挂起生成拍板表，人工标注后再执行；每日启动先复盘昨日岗位与职责并把结论回写配置；拍板按阈值渐进攒批；标注样本覆盖主要场景后，同类已知岗位可按学到的口径自行判定，未覆盖的新场景仍交人工拍板；全程台账去重、当日复盘；当日打招呼累计达到目标份数即停止继续检索。每条岗位先过 §0.4 长期规则：技术栈严格匹配（简历没有的栈不投）、大厂排除、外包公司知识库自动学习与公司级拦截。

## 安装与宿主适配

本技能与宿主 AI 工具解耦：一份指令文件（`SKILL.md`）+ 一组 Python CLI 脚本 + 规则参考 + 画像模板 + 版本清单。宿主只需具备三项能力：浏览器自动化、终端命令执行、本地文件读写。

1. **保持整目录**：`boss-job-apply/` 原样复制，`scripts/`、`references/`、`assets/` 之间的相对引用不能拆散；文件夹名与 frontmatter `name` 一致（`boss-job-apply`）。
2. **按宿主工具放置**（常见约定，具体路径以宿主官方文档为准）：
   - 豆包工作区（✅ 已实测）：`.user_skills/boss-job-apply/`（与内置 `.skills/` 平级）；
   - Claude Code（⚠️ 通用适配目标，未逐一实测）：`~/.claude/skills/boss-job-apply/`；
   - Cursor（⚠️ 待适配）：把本指令放入项目 `.cursor/rules/`，脚本与模板随项目固定目录存放；
   - Codex / OpenAI 类（⚠️ 待适配）：在 `AGENTS.md` 中引用本 `SKILL.md`，脚本随仓库存放；
   - Windsurf（⚠️ 待适配）：放入 `.windsurf/rules/`；
   - 其他工具（⚠️ 待适配）：把 `SKILL.md` 作为全局或项目指令加载，同目录保留 `scripts/`、`references/`、`assets/`。
   - 目前推荐且验证可用的宿主只有豆包办公；其他宿主装载后若指令不识别、脚本路径或浏览器调用不通，按本节适配约定对照宿主文档微调。

5. **触发方式**：在宿主对话中描述 BOSS 直聘/打招呼/投递/筛岗等任务时加载本指令；也可以直接说「按 boss-job-apply 流程跑今日投递」。

## 前置准备

1. `profile.json` 初始化见 §0.1；登录核验见 §0，登录态失效、验证码、扫码一律交本人接管，不绕过。
2. 工作目录产物：`candidates.json`（采集卡片）、`ranked.json`/`batch.json`（排序批次）、`details.jsonl`（详情复核行）、`hold.json`（待定池）、`ledger.json`（台账）、`review_yesterday.json`（昨日复盘小结）、`risk_events.jsonl`（风控熔断事件）。这些产物只服务当日运行与断点续跑，不进启动上下文、不回写正本、不提交仓库。

## 工作流

### 0. 打开浏览器与登录核验

- 用宿主工具的浏览器自动化能力打开岗位页，导航到 BOSS 直聘求职者岗位页：
  `https://www.zhipin.com/web/geek/jobs?city=<城市码>&query=<关键词>`（城市码填 `profile.json` 的 `city_code`；未知时从页面城市选择器读取）。
- 登录核验：页面显示本人账号头像/昵称即为已登录；若跳到登录页、出现扫码、滑块或设备验证，停下手头操作交本人接管，不绕过、不尝试自动登录。
- 登录成功后回到岗位列表页，再开始后续流程；全程保持该浏览器标签会话，不另开爬虫或未公开接口。
- **首次使用的新用户**：先按 §0.1 完成登录引导、简历提取与画像确认；画像未经本人确认前，不检索岗位、不打招呼。

### 0.1 初始化 profile.json（首次使用 · 新用户引导流程）

新安装本技能的用户按下面顺序走完引导，画像确认后才允许开始投递：

1. **引导登录**：先引导本人在浏览器完成 BOSS 直聘网页登录（§0）；登录态有效后才进入下一步，未登录不采集简历、不建台账。
2. **复制模板**：把技能目录 `assets/profile.example.json` 复制到本次工作目录为 `profile.json`（技能目录路径以当前环境已安装技能的位置为准）。
3. **从简历提取配置**：在已登录会话中打开本人主页/在线简历，采集城市、工作年限、学历、技术栈、期望薪资、求职状态；再读在线简历与附件简历的「个人优势」「项目经历」（角色、职责、所用技术栈、可量化成果）提炼成画像条目。只读本人账号可见内容，不改写 BOSS 简历，不采集未公开信息；附件简历需本人同意后再打开，不绕过查看限制。
4. **澄清反问（拿不准必须问，不用默认值顶替）**：简历看不出、表述模糊或自相矛盾的字段，逐项反问本人，至少覆盖：投递目标方向与目标岗位名、期望薪资区间、目标城市、哪些技术栈可投/哪些不投、是否接受外包驻场、单休、特定行业、作息安排。本人当场补充的信息直接采用；禁止臆造年限、学历、技术栈、薪资、优势、项目经历与弱点。
5. **画像确认闸门**：把提取并澄清后的画像列成条目回显给本人核对；本人确认通过后才初始化台账、进入检索与投递。本人明确拒绝填写的字段保留占位符，对应岗位在详情复核时降级人工判断，不按默认值擅自放行。
6. `profile.json` 仅存本地工作目录，不写入技能文件、不提交任何仓库。

### 0.2 版本自检与升级提示

- 启动当日投递任务前，先运行版本自检：

```bash
python scripts/version_check.py
```

- 脚本对比本地 `VERSION` 与上游仓库同路径版本；网络不可达时跳过自检，不阻断投递流程。
- 若提示有新版本：向本人展示**新版本号、本地版本号、相对当前版本的改动摘要**（改动条目从 `references/changelog.md` 对应版本提取），并提示按 README「版本与升级」一节更新技能目录；**未获本人确认前不自动覆盖本地技能文件**，继续使用当前版本跑任务。
- 本地版本高于上游时，提示可能为本地定制分支，不自动回退。
- **通知必须到达本人**：版本自检是启动必做项，结果不能只留在日志或终端输出里。上游有新版本时，把「新版本号、本地版本号、改动摘要、升级步骤」放在当天汇报或会话回复的**开头**醒目位置；出现 `upgrade_available=true` 却未告知本人，视为启动协议未完成。宿主连续多日未运行时自检不会触发，可请本人在 GitHub 仓库点 Watch → Custom → Releases 订阅发布通知作为补充。
- **发版命名约定**：创建 GitHub Release 时，标题只写版本号（如 `v1.6.2`），不带中文描述；版本改动摘要写进 Release 正文，不塞进标题。

### 0.3 拟人节奏与风控熔断（全流程强制）

本技能的所有网页操作必须像真人操作，不按固定毫秒批量点击；完整规则见 `references/pacing.md`，参数读 `profile.json` 的 `pacing` 与 `risk_guard`。

**节奏要求（全程遵守）**

1. **随机间隔**：每个动作的等待从 `pacing.action_ranges` 区间内随机取值，禁止写死常量；同类动作连续出现时间隔要变化。
2. **分段滚动**：每次滚 300–600px，停 1–3 秒读卡片，再继续；接近底部放慢，直到卡片数量不再增长。禁止一步滚到底、瞬移末页。
2a. **悬停后再点击**：点卡片或「立即沟通」按钮前，先悬停到目标上、小幅移动并停顿 `hover_pre_click`（默认 0.5–1.5 秒）再按下，按下后随机停顿 `click_post`（默认 1–2.5 秒）再读结果；禁止连点、禁止坐标猛戳、禁止无悬停直按。
3. **阅读停留**：详情页打开先停 2–5 秒，读 JD 至少 8–20 秒，JD 越长停越久；不读完不打招呼。
4. **打招呼节律**：打招呼前后各停 3–7 秒、4–10 秒；两条之间间隔按 `pacing.mode` 档位（conservative 2–5 分钟 / standard 1–2.5 分钟 / active 40–90 秒）；每小时不超过档位上限（默认 `standard` 20 条），连续操作到档位时长后休息，只在 `pacing.active_hours` 内发起打招呼。
5. **节奏表可选**：需要固定节奏表时跑 `python scripts/pacing_plan.py --greets N --profile profile.json [--mode conservative|standard|active]`，按输出逐条等待；脚本只给等待值，不点页面。
6. **真实浏览轨迹**：从列表点卡片进详情（保留列表来源），看完返回列表再进下一条；禁止脚本化深链批量直跳详情链接；每复核 5–8 条回列表回看一小段做对比。

**风控熔断（最高优先级，覆盖其他一切指令）**

- 出现验证码、滑块、点选/设备/人脸验证、安全验证页，或「操作过于频繁」「请稍后再试」「访问异常」「账号存在风险」、沟通按钮变灰、消息发送失败等任一信号：**立即停止当次全部自动操作**，保留页面原状，不刷新、不试探、不重试。
- 把信号原文、时间、当时动作如实报给本人，由本人决定人工验证后继续还是当日收工；可继续时冷却 `risk_guard.cooldown_minutes`（默认 120 分钟）再启动，当日剩余份额减半。
- 当日熔断达到 `risk_guard.max_triggers_per_day`（默认 2）即当日终止自动投递；触发计数写入台账状态（按自然日计数、每日启动清零），第二次触发置当日终止标志，剩余招呼目标顺延次日，不当日补投。
- 事件写入工作目录 `risk_events.jsonl`，供复盘判断是否该继续放量。
- **绝对禁止**：过验证码/破滑块、伪造设备指纹或 UA、换 IP/代理池、多账号轮投、调未公开接口、并发多标签批量打招呼、被拦后加速冲量、靠降低门槛凑当日份数。
- 首次使用或近期被验证过的账号，按 `pacing.ramp_up_note` 梯度放量，不直接冲满 `meta.daily_goal`。

### 0.4 长期规则（每条岗位都先过）

1. **技术栈严格匹配**：只投 `profile.json` 中本人可覆盖栈（Java/JVM、Spring 生态、MySQL/Redis/RocketMQ/ES、Python+FastAPI、LangChain/LangGraph、RAG 全链路、Vue3+TS、Java+Python+Vue 全栈协同）。JD 必需项出现本人没有的栈（iOS/Android/Flutter/React Native/Swift/Kotlin/Unity/C#/.NET/PHP、Go 或 C/C++ 主栈、大数据 Flink/Spark、推理部署 TensorRT/vLLM、模型训练/微调为主责）直接跳过，记 `stack:`；React 仅「了解/加分」可放行，React+移动端组合一律排除。标题写「全栈开发工程师」不等于匹配。
2. **大厂排除**：画像 `excluded_companies` 列出的互联网/车企/物流/终端大厂（阿里系含优酷、大麦娱乐/大麦、钉钉、阿里云、高德、盒马，腾讯、字节、美团、京东、百度、网易、快手、拼多多、小红书、B站、滴滴、携程、得物、贝壳、58；吉利、比亚迪、蔚来、小鹏、理想、长城、奇瑞；顺丰、中通、圆通、申通、韵达、极兔、德邦；华为、小米、OPPO、vivo、海康、大华、中兴、联想）一律不投，记 `dachang:`。子公司/厂牌名同样算（如优酷挂「大麦娱乐」主体）。
3. **外包/外派公司知识库（自动学习）**：`outsource_kb.json` 记录已被证实为外包/驻场/外派的公司。任一岗位 JD 含证据词（外包岗/驻场/外派/派遣/人力外包/客户现场/驻客户/驻银行/驻行/银行现场/行方办公/驻点/外协/BPO/劳务，否定表述豁免）即把该公司写入知识库并记住；之后该公司任何岗位即使 JD 未写外包也直接跳过，记 `outsource_kb:`。知识库跨日累积、去重、只增不减；人工确认是甲方可手工移出。用户点名已收录：汉克时代、昌瑞、云象、五十五只猫、先进数通。
4. **外地 base 排除**：目标城市固定为杭州。标题出现外地城市且不含「杭州」（如「全栈开发工程师【base安徽合肥】」「Java开发岗（工作地点温州总部）」）直接跳过；JD 正文「base/工作地点/工作地址/常驻」后 20 字内出现外地城市且同段无「杭州」也跳过，记 `base:<城市>`。外地城市覆盖省外主要城市及浙江省内非杭州城市（温州、绍兴、台州、金华、嘉兴、湖州、衢州、丽水、舟山等）。边界：同一句里「base：上海，偶尔杭州出差」这类混写会被「杭州」字样豁免，遇到时按标题主 base 人工判断。
5. **猎头岗位排除**：职位卡片左上角带「猎头」标签，或职位信息、招聘者身份、公司名含猎头、人才顾问、人力资源服务等猎头含义的，在列表层直接跳过，不进详情复核、不点沟通，记 `headhunter:`。该判定先于薪资、活跃度等其他判断执行。

### 0.5 启动前置硬约束（每次开工第一步，先于检索与复盘）

- **每次启动投递任务，第一步先读上下文配置正本**：先读取精简配置正本（飞书《张大帅 BOSS 求职全局配置（精简正本）》）与本地台账 `ledger.json`/当日流水，逐条核对求职者画像、轮转方向词清单、薪资交集口径与 `max_hi` 上限硬线、硬排除清单、活跃度门槛、技术栈匹配口径、动作边界与风控熔断规则；确认口径与本地记录一致、登录态有效后，才允许开始检索。
- **配置分层，防止上下文稀释**：配置分两份文档。精简正本只放现行规则与画像，启动时全文必读；历史记录库只存每日流水、复盘轮次与误投留痕，需要时按日期检索，不进启动上下文。对话中的新口径当天写入精简正本；每日投递结果只写历史记录库。宿主中未配置该文档时，用 `profile.json` 加本地规则文件充当正本，并在 README 注明对应关系。拍板表、标注结果、外包知识库、台账、复盘小结、风控事件均为工作目录产物，不进启动上下文、不回写正本、不提交仓库。
- 配置未读、或本地台账/脚本口径与配置正本冲突时，先回配置正本核对，**不凭记忆开工**；配置确认无误后再进入 §1 复盘昨日岗位。
- 配置正本中「启动协议」与「每日投递流程」为最高优先级执行约束，任何一轮投递都不得跳过或事后补读。

### 1. 每日启动：复盘昨日岗位与职责，回写配置

- 打开 BOSS 消息列表并结合台账 `ledger.json` 的 `applied` 记录，逐条回看昨日已沟通岗位：岗位职责/JD 要点、方向、技术栈、招聘方回复或被拒原因。
- 归纳昨日样本：哪些方向/栈/职责被正向回应，哪些被拒或不合适；把结论沉淀回写 `profile.json`：命中关键词、加分词、短板、标题/主体排除词表、`rules` 口径；复盘小结写入工作目录 `review_yesterday.json`。
- 招聘方回复措辞含糊或读不懂时，先向本人澄清确认，不臆测对方意图；复盘结论只更新画像与词表，**不放宽硬排除清单**。
- 用 `ledger.py status` 查看台账累计，作为复盘基数。

### 2. 关键词轮转检索并采集卡片

- **轮转顺序**：按 `profile.json` 的 `expectation.positions` 顺序逐个跑关键词；**强制以配置正本的关键词清单为准，不得擅自增删词或改序**（本人主循环 23 词；原补充池 ERP/CRM/MCP/知识库/NL2SQL 已于 2026-11-26 停用，不再跑）；选词只取本人简历技术栈可覆盖的方向；不写 Python 爬虫、不调用未公开接口。
- **城市固定**：搜索前把城市固定为 `profile.json` 目标城市（URL `city` 参数与页面城市选择器双重确认），外地 base 岗位不采集。
- **采集前置视口校验（硬约束）**：每个关键词开始采集前，先读真实 `window.innerWidth`，**须 ≥1200 才允许采集**；远程浏览器窗口可能在会话中途缩窄（如缩到 655px 分栏），且 `new_tab` 会继承当前窄窗口、CDP 窗口管理/桌面调窗在该环境不可用。若实测 <1200：先设法恢复宽屏窗口再采；恢复不了时，该词在窄屏下只会渲染十几条即「假到底」，**不得把这种结果当作全量**——要么标记该词欠采待宽屏补采，要么仅按「增量首屏」口径处理（新岗排在列表顶部，首屏可覆盖增量）并在台账注明视口受限。脚本侧 `collect_resume.scroll_session` / `collect_full.gather_all` 起始即做此校验并落 `viewport` 标记。
- **单关键词全量采集（滚动到底协议，硬约束）**：进入该关键词结果页后分段下滚，每滚一段就把当前渲染卡片按 eid **边滚边累积**进去重字典——BOSS 列表为虚拟渲染、屏外节点会被卸载，禁止回到顶部后一次性提取。**到底后下一批卡片可能延迟约 5–10 秒才加载**，须等足约 10 秒「卡片总数不再增加、页面滚动高度不再变化」才判定该词到底，禁止卡片数首次不变就提前停止。**窄屏分栏视口会把列表截断成十几条，采集必须在宽屏完整列表视口进行**（发现只加载十几条且久不增长时，新开宽屏标签重采）。到底后再点「下一页」逐页翻到末页、按钮消失或置灰为止。**每个关键词都必须遍历全部页、全部卡片，禁止只看首屏或前几页**；一次搜索可能有几百条结果，全部纳入候选池。
- **采完一个再换下一个**：当前关键词滚动到底、翻遍末页、按列表从上到下逐张采集完成后，进入 §3–§5 的预筛、复核、打招呼闭环；**该词全部新候选逐条详情复核处理完后，才换下一个关键词**。结果汇入统一台账去重。关键词尚未采完、新候选尚未处理完时不跳词、不并行混采。
- **顺序采集**：按 BOSS 列表从上到下逐张采集，不跳页、不漏页；记录招聘者活跃标签（刚刚活跃/今日活跃/3日内活跃/本周活跃/本月活跃等）。
- 卡片薪资加密，列表层只采集标题/公司/链接/活跃标签；真实薪资与完整 JD 留到详情页读。
- 多关键词结果合并、按 eid 去重后汇总为 `candidates.json`：`[{"eid","title","company","salary","active","url"}]`，eid 取链接 `job_detail/` 末段（去掉 `.html`）。
- **停止条件**：台账 `applied` 累计达到 `meta.daily_goal`（示例 100 份）即停止继续检索和打招呼；所有关键词跑完仍未达标时，进入 §7 复盘缺口，仅在硬排除项全部保留的前提下扩大可选方向。

### 3. 预筛与排序

```bash
python scripts/rank_candidates.py --input candidates.json --profile profile.json \
  --ledger ledger.json --out ranked.json --batch 12
```

台账去重（已投/已跳过）、标题与主体硬排除（含大厂名单与外包知识库公司级黑名单 `outsource_kb:`）、活跃度僵尸岗剔除、薪资无交集剔除；剩余按关键词打分排序，高分优先进详情复核。被剔除项落在 `ranked.json.dropped`，原因可追溯。

### 4. 详情页逐条复核

- 逐条打开岗位详情，读取真实薪资、学历、经验、地点、完整 JD。
- 判定依据 `references/filters.md`：先过 §1 薪资口径，再过 §2.2 技术栈严格匹配（JD 必需项出现本人没有的栈即 exclude，记 `stack:`），再过 §3 硬排除清单（大厂、外包知识库公司、角色方向）与 §4 复核清单（含招聘者活跃度 ≤3 天、岗位未过期）。
- JD 读到后先做外包证据扫描：命中即 `outsource_kb.learn(company, jd)` 入库并跳过该岗位（`outsource_kb:`）。
- 三分类：
  - **apply**：复核清单全部通过，进打招呼；
  - **exclude**：命中硬排除，记台账 skipped 并写原因；
  - **hold**：经验深度、主体性质、方向边界、硬门槛存疑，进 `hold.json`；不自行放行，也不自行排除（学习饱和后的自行判定规则见 §6）。
- 复核行写入 `details.jsonl`：`{eid, title, company, salary, exp, edu, city, jd, full}`。

### 5. 打招呼（仅限 apply）

- 点「立即沟通」，发送账号默认招呼语；不附附件简历、不发在线简历；已显示「继续沟通」的职位不重复点。
- **按拟人节奏发送**（见 §0.3 与 `references/pacing.md`）：打招呼前停 3–7 秒模拟确认，点击后停 4–10 秒看结果再返回；两条之间留 2–5 分钟间隙；累计每小时不超过 `pacing.hourly_greet_cap`，连续 20–30 分钟必须休息；只在该时段窗口内发起。
- **每投一条回写台账**（边投边记，便于随时中止与断点续跑）：

```bash
python scripts/ledger.py applied-append --eid EID --company C --title T --salary S --match "命中方向"
python scripts/ledger.py skip-append --eid EID --reason "排除原因" [--company C --title T --salary S]
```

- 不主动回复招聘方；猎头弹层提示「主动联系后简历可见」时取消，不计新增；同公司同职责重复链接审慎去重。
- 打招呼过程中一旦命中 §0.3 的风控信号，立即停发并按熔断流程处置，不得为了凑够 `meta.daily_goal` 继续点击。

### 6. 待定拍板闭环（渐进攒批 + 饱和后自行判定）

**6.1 渐进攒批**

- 投递过程中持续收集 hold 岗位；`hold.json` 每攒够 `profile.json` 的 `decision.hold_batch_size`（默认 6 条），就生成一批拍板表，不必等当日全部跑完：

```bash
python scripts/build_decision_sheet.py --input hold_batch.json --out decision_sheet_<日期>_batch<N>.xlsx
```

- 拍板表附**完整 JD**（不是截断要点），导入任意在线表格或本地 Excel/CSV，交本人标注「可投 / 不投」；不足一批的剩余挂起，并入下一批。
- **飞书拍板文档（2026-11-25 用户明确）**：宿主支持飞书文档时（如豆包办公用 `lark-cli docs +create`），每批同时生成一份飞书拍板文档，列为序号、公司、岗位、薪资、招聘者活跃度、待定原因、职位链接、完整 JD，以及留给本人填写的「你的决定」「备注」两栏；文档链接放在当天汇报的**开头**并写明「待拍板 N 条」，提醒本人拍板。宿主不支持飞书文档时用 xlsx，并在汇报开头列出文件路径。拿不准的岗位一律走这里，不自行放行也不自行排除。

**6.2 标注解析与执行**

标注回表后解析分组：

```bash
python scripts/parse_annotation.py --sheet decision_sheet_<日期>_batch<N>.xlsx --out annotation_result_<批次>.json
```

- `apply` 组按 §5 补打招呼；`exclude` 组记台账 skipped；`blank` 继续挂起。
- 把标注结论沉淀回写：新增排除类别、放行口径更新到 `profile.json` 词表与 `filters.md` 对应小节，形成学习闭环。

**6.3 学习饱和判定**

- 每完成一批标注，统计已标注样本数与场景覆盖度（方向、栈、主体性质、排除类别是否都已有样本）。
- 当满足 `decision.saturation.min_annotated_samples` 且主要场景已被标注样本覆盖时，视为进入饱和状态：**同类已知场景**的 hold 岗位可按已学到的口径自行判定（apply/exclude），判定理由记入台账；
- **未覆盖的新场景、新方向、新主体类型**仍进拍板表交本人标注；硬排除清单 §3 中的类别任何时候都不自动放行。
- 是否允许饱和后自行判定由 `decision.saturation.auto_decide_when_covered` 控制；关闭时所有 hold 一律走人工拍板，不自行拍板。
- 自行判定拿不准时，降级为人工拍板，不要硬放行。

### 7. 当日复盘

统计 applied/skipped 数量、方向与薪资分布、回复/被拒情况；对照画像找偏差。当日流水与复盘轮次写入历史记录库（无在线文档时写入本地台账与复盘小结），不回写精简正本；沉淀后的现行口径变更才更新正本与 `profile.json`。当日 `applied` 未达 `meta.daily_goal` 且全部关键词已跑完时，仅在硬排除项全部保留的前提下扩大可选方向；不放行硬排除类别，也不靠降低活跃度/薪资门槛凑数。

## 边界

- 网站信息采集走浏览器自动化；Python 只做本地去重、排序、台账、制表、节奏计算等后处理。
- 遇到验证码、扫码、设备验证、登录态失效：停下手头操作，交本人接管；不绕过、不降速硬冲。
- 节奏与熔断只能降低风控概率，不能保证账号不被限制；账号一旦受限立即停用本技能并按平台流程申诉。
- 个人信息（姓名、联系方式、简历项目）只进本地 `profile.json` 工作目录，不写入技能文件。

## 1. 薪资口径

岗位薪资区间与画像目标区间 `[lo, hi]`（如 18–25K）**有交集即投**：

- 判定：岗位下限 ≤ `hi` 且岗位上限 ≥ `lo`，闭区间相交，边界值包含。
- 上限硬线：岗位薪资上限 > `max_hi`（默认 35K）一律不投，即使与目标区间有交集；示例 `20~40K`、`25~45K` 不投。`max_hi` 读画像 `expectation.salary_band.max_hi`，未配置时按 35K 兜底。
- 正例：`12~18`（上限 18 包含）、`15~25`、`25~35`（下限 25 包含、上限 35 包含）。
- 反例：`8~14K`（上限 < lo）、`28~40K`（下限 > hi）、`20~40K` / `25~45K`（上限 > max_hi）不投。
- 薪资带 `·13薪/·14薪/年终奖` 不影响区间判定，只取 K 数；`N·薪` 不是年限。
- 列表卡片薪资加密，**必须进详情页读真实薪资**，不得凭卡片标签判断。

## 2. 纳入原则

- 方向命中：画像 `expectation.positions` 列出的目标方向（示例：后端/全栈/AI 应用/智能体/知识库等）。
- 技术栈可覆盖：画像主栈能对上 JD 必需项；可选加分栈不要求全会；「全栈/开发工程师」标题本身不放行，按下节严格匹配。
- 甲方自研团队即可，不按公司人数规模、是否上市设限；A 股上市传统软件/中型公司可投。唯一例外：**公司规模 0-20 人（含「少于 20 人」「20 人以下」）不投**（2026-11-25 本人明确）。
- 行业不卡：以技术栈可覆盖为准，详见画像 `track_policy`。
- 年限：以画像 `profile.work_years` 为准；偏资深的低年限岗可投，远超本人年限的谨慎复核。
- 学历口径见画像 `rules.education`：按本人学历填写可投/排除门槛。
- 放行补充：非主流栈仅为次要要求、主栈契合时不单独否决；全栈年限软差距、主栈契合时可尝试；主栈硬年限（JD 硬需画像短板中列出的多年经验）仍不投。

### 2.2 技术栈严格匹配（优先于方向词）

- **判定原则**：以画像 `profile.main_stack` 与 `profile.secondary_stack`（本人可覆盖栈）为唯一依据，`profile.weak_points` 列出的缺失栈即为硬不匹配；JD「任职要求」中的必需项必须能被覆盖；标题出现「全栈/开发工程师/研发」不等于匹配。
- **可覆盖栈（示例画像）**：Java 基础与 JVM（集合/并发/锁/线程池/AQS/GC/类加载）、Spring Boot/Spring AI/MyBatis-Plus、Spring Cloud/Alibaba、Dubbo、Nacos、Sentinel、分布式事务、DDD；MySQL 调优、Redis（分布式锁/持久化）、RocketMQ、Elasticsearch；Python+FastAPI（异步/SSE）、LangChain/LangGraph、RAG 全链路（BGE-M3→Milvus→RRF→Rerank→LLM）、MongoDB/MinIO/PyTorch；Vue 3+TS+Vite+Pinia+Router/RBAC+Element Plus；Java+Python+Vue 全栈协同、SDD、AI 编程工具。
- **硬不匹配（必需项命中即跳过，记 `stack:`）**：iOS、Android、Flutter、React Native、Swift、Kotlin、Objective-C、Unity、Cocos、C#/.NET、PHP、Go 为主栈、C/C++ 主栈、原生小程序、游戏客户端；Flink/Spark/Hadoop/ClickHouse 大数据实时链路为主责；TensorRT/vLLM/Triton 推理部署；模型训练/微调（LoRA/SFT/DPO）为主岗；推荐算法、数据标注、测试开发为主岗。
- **React 规则**：JD 仅「了解/加分/优先」可放行；Vue 与 React 并列为次要可选可放行；只要出现「React + iOS/Android/React Native/原生」组合或 React 为前端主责且要求移动端，直接排除。
- **豁免写法**：命中词出现在「优先/加分/了解/可选/非必需/不要求/无需」语境且非硬性必需时豁免；无法判断是否必需时进 hold 拍板表，不自行放行。
- **示例教训（2026-11-24）**：杭州米加健康集团「全栈开发工程师」要求 React + iOS/Android，本人均无，属误投；此后同组合一律跳过。

### 2.1 检索轮转与全量采集协议

- **关键词顺序**：选词与轮转顺序读画像 `expectation.positions`，只列本人简历技术栈可覆盖的方向；顺序即处理顺序，不按热度随意调换。**强制以配置正本关键词清单为准，不得擅自增删词或改序**；本人主循环 23 词，原补充池 ERP/CRM/MCP/知识库/NL2SQL 已于 2026-11-26 停用。
- **单关键词全量遍历**：每个关键词结果页必须反复滚动到底、直到卡片数量不再增长，再逐页翻到末页（「下一页」消失或置灰）；一次搜索可能有几百条结果，禁止只看首屏或前几页截断采集。**到底后下一批卡片可能延迟约 5–10 秒加载，须等足约 10 秒无新增再判到底**；**窄屏分栏视口会截断列表成十几条，采集须在宽屏完整列表视口进行**，发现久不增长时新开宽屏标签重采。
- **采完一个再换下一个**：当前关键词采集完成后，进入预筛、详情复核、三分类与打招呼闭环，结果汇入统一台账去重；闭环跑完再轮到下一个关键词，未采完不跳词。
- **逐候选复核**：每个纳入候选池的岗位都要走 §4 复核清单，不得跳过详情页直接按列表标签判定。
- **达标停止**：台账 `applied` 累计达到画像 `meta.daily_goal` 即停止继续检索与打招呼；全部关键词跑完仍未达标，按 §8 复盘缺口再扩方向，不放宽 §3 硬排除清单、不降低活跃度与薪资门槛凑数。

## 4. 打招呼前复核清单

逐条核对，全部满足才走打招呼：

1. 方向命中目标方向之一；
2. 薪资与目标区间有交集（见 §1）；
3. 学历可过、无全日制/统招/院校硬门槛；
4. 公司为甲方自研，非外包驻场/猎头代招；
5. JD 不要求简历缺失的硬技能或多年弱点经验；
6. 不在硬排除清单 §3 任一类别；
7. 招聘者活跃度 ≤3 天（刚刚活跃/今日活跃/3日内活跃）；详情页招聘者信息区提取，打招呼前必须核验；

9. 无待核疑点（主体性质、驻场痕迹、方向边界、经验深度存疑 → 进拍板表，见 §5）。

## 5. 边缘待定 → 人工拍板表协议

**不确定的岗位不自行放行，也不自行排除**：经验深度待核、主体外包嫌疑、方向边缘、硬门槛模糊、行业匹配存疑等，一律进 hold 池。

### 5.1 渐进攒批

1. 投递过程中持续收集待定岗位；`hold.json` 每达到画像 `decision.hold_batch_size`（默认 6 条）就生成一批拍板表，不必等当日全部跑完；不足一批的剩余挂起并入下一批。
2. 拍板表列：序号/公司/岗位/薪资/经验/学历/地点/待定原因/岗位链接/完整 JD/你的决定；表内必须附**完整 JD**（不是截断要点），供本人核实。
3. 交本人人工标注「可投 / 不投」；表名按批次区分，如 `decision_sheet_<日期>_batch<N>.xlsx`。
4. 按标注执行：可投的补打招呼并记台账；不投的记 skipped 并写原因；空值继续挂起。
5. 把标注结论回写到画像规则：新增的排除类别、放行口径沉淀进 `profile.json` 与本文件对应小节，形成学习闭环。

### 5.2 学习饱和后自行判定

- 每完成一批标注，统计已标注样本数与场景覆盖度（方向、技术栈、主体性质、排除类别是否都有样本）。
- 满足画像 `decision.saturation.min_annotated_samples` 且主要场景已被覆盖，同时 `auto_decide_when_covered` 为 true 时，**同类已知场景**的 hold 岗位可按已学到的口径自行判定 apply/exclude，判定理由记入台账。
- 以下情况仍必须进拍板表人工标注：未覆盖的新方向/新技术栈/新主体类型；饱和开关关闭；自行判定拿不准。
- **硬排除清单 §3 的类别任何时候都不自动放行**；饱和自行判定只适用于已覆盖的边缘场景，不覆盖硬排除项。

## 6. 行动边界

- 只发 BOSS 当前默认个性化招呼语；不附附件简历、不主动发在线简历，未获本人另行授权前一律不发；
- 已显示「继续沟通」的职位不重复点击；
- 不主动回复招聘方聊天，除非本人另行要求；
- 猎头弹层提示「主动联系后猎头可见简历」时取消，不计入新增；

## 7. 排序打分启发式

候选池先去重（台账已投/已跳过/eid 集合），再打分排序，高分优先进详情复核。

- 词表与权重读 `profile.json` 的 `scoring.bonus` / `scoring.penalty`（每项：`words` 数组 + `points` 分值）；未配置时脚本使用内置通用默认启发式。
- 内置默认示例：后端/服务端 +15；全栈 +8；资深/高级/专家 +3；项目制/外派/驻场/派遣 -15；组长/负责人/leader/总监/经理 -5；游戏/区块链/Web3/催收/量化/嵌入式/IoT -10；匿名壳/某大型/某知名 -25；基础设施/算力/数据平台/运维平台/工具链/推理/模型部署 -30；售前/解决方案/交付 -15。
- 方向与主栈相关的加减分词（具体语言、框架、赛道）写进本人 `profile.json`，不固化在技能文件里；可按拍板标注反馈持续调整。

## 8. 每日复盘与配置回写

1. 每日启动先回看昨日已沟通岗位（消息列表 + 台账 `applied`）：岗位职责/JD 要点、方向、技术栈、招聘方回复或被拒原因。
2. 归纳哪些方向/栈/职责被正向回应、哪些被拒或不合适；把结论回写 `profile.json`：命中关键词、加分词、短板、标题/主体排除词表、`rules` 口径；复盘小结写入工作目录 `review_yesterday.json`，画像 `review.yesterday_summary` 与 `review.sunk_rules` 同步更新。
3. 回复措辞含糊或读不懂时，先向本人澄清确认，不臆测对方意图。
4. 复盘只校准画像与词表，**不放宽 §3 硬排除清单**；当日未达目标时也不放行硬排除类别。
5. **回写去向（配置分层）**：在线文档场景，当日投递流水、复盘轮次、误投留痕写入历史记录库，不写回精简正本；只有沉淀后的现行规则/画像口径变更才更新正本。未配置在线文档时，正本对应本地 `profile.json` 与规则文件，流水与小结写入工作目录 `ledger.json` / `review_yesterday.json` / `details.jsonl` 等产物；拍板表、标注结果、外包知识库、风控事件同属工作目录产物，不回写正本、不进启动上下文。
